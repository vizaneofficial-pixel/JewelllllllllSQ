# PART 2 — LIVE SELLING: CORE CONCEPT

Create a dedicated section named **Live Selling**.

This section is designed for someone physically selling products at an exhibition, jewellery stall, pop-up shop, or retail event.

The user will be interacting with it while customers are continuously approaching the stall.

The interaction must be exceptionally fast.

### Core principle

A normal sale should require only ONE TAP.

The user should be able to:
1. See available products.
2. Tap the product.
3. Have the sale registered immediately.
4. Move on to the next customer.

The entire normal sale registration should take less than three seconds.

Do not turn this into a complicated conventional POS checkout system.

The interface should be distraction-free and optimized for continuous selling.

### 2.1 Integration

Add Live Selling to the existing StallIQ navigation.

It must be available on both desktop and mobile layouts without redesigning either.

When the user opens Live Selling, it should display the active project's available inventory.

The system must use existing project data, product prices, purchase costs, quantities, and categories.

Never create separate sample inventory or duplicate financial calculations.

# PART 4 — ONE-TAP SALE REGISTRATION

This is the most important interaction.

When a user taps an available product:

1. Immediately register one unit as sold at its predetermined selling price.
2. Record the transaction.
3. Reduce the available quantity by one, if inventory quantity is tracked.
4. Update actual revenue.
5. Update realized gross profit.
6. Update the sales history.
7. Show subtle visual and haptic feedback where supported.

There must be:
- No mandatory checkout screen.
- No confirmation popup.
- No mandatory customer information.
- No mandatory payment selection.
- No unnecessary intermediate steps.

A normal full-price sale must happen with one tap.

### 4.1 Products without planned quantities

Some existing products may not have a planned quantity.

Do not treat an unspecified quantity as zero.

For such products, allow sales to be recorded while clearly distinguishing unknown or untracked stock from actual zero remaining stock.

### 4.2 Sold-out protection

If a product has a tracked quantity of zero:
- Clearly mark it sold out.
- Disable normal sale registration.
- Prevent accidental negative inventory.
- Allow stock correction through the appropriate inventory management workflow.

Do not allow sales beyond available stock unless the user deliberately uses an authorized stock override.

# PART 5 — QUICK DISCOUNTS AND BARGAINING

The selling price of each product is already defined in StallIQ inventory.

However, during actual stall selling, customers may negotiate.

The Live Selling system must make bargaining discounts extremely fast.

### 5.1 Discount selector

Provide these options:

- Full Price.
- −₹20.
- −₹30.
- −₹40.
- −₹50.
- Custom Discount.

These are fixed rupee deductions from the original selling price.

Example:

Original product selling price: ₹500.

| Selection | Final selling price |
|---|---:|
| Full Price | ₹500 |
| −₹20 | ₹480 |
| −₹30 | ₹470 |
| −₹40 | ₹460 |
| −₹50 | ₹450 |

### 5.2 Discount interaction

Normal full-price sale:
- One tap registers the sale immediately.

Discounted sale:
- Tapping the product opens a compact discount selector.
- Selecting the desired discount immediately registers the sale.
- No additional confirmation screen.
- Keep the process as close to two taps as possible.

Custom discount:
- Allow entering any fixed rupee amount.
- Use a compact numeric input.
- Do not require an unnecessarily complicated form.

### 5.3 Discount validation

- Never allow a discount that makes the final selling price zero or negative.
- Clearly display the final selling price.
- Record original selling price and actual selling price separately.
- Record the exact discount amount.
- Calculate realized profit using the actual discounted price.
- Preserve the original inventory selling price.
- Never permanently change the product's default selling price just because a customer negotiated a discount.

### 5.4 Quantity and discounts

When a customer purchases multiple units:
- Allow applying the same per-unit discount to all units.
- Calculate the correct total discount.
- Record the quantity and actual unit selling price.
- Ensure the discount cannot accidentally be applied twice.

Example:

Three units at ₹500 each, with a ₹30 discount per unit.

Original total: ₹1,500.

Total discount: ₹90.

Actual revenue: ₹1,410.

Realized profit must be calculated using the actual selling amount minus the cost of all three units.

# PART 13 — RELIABLE TRANSACTION DATA MODEL

Inspect the existing database architecture and extend it without breaking existing data.

Implement a proper sales transaction model.

Each transaction should contain the relevant fields:

- Unique transaction ID.
- User ID.
- Project ID.
- Selling session ID.
- Product ID.
- Product name snapshot.
- Category snapshot.
- Quantity.
- Original unit selling price.
- Actual unit selling price.
- Per-unit discount.
- Total discount.
- Original total value.
- Actual total revenue.
- Purchase cost per unit snapshot.
- Total cost of goods sold.
- Realized gross profit.
- Payment method.
- Transaction timestamp.
- Transaction status.
- Synchronization status.
- Reversal or correction reference, if applicable.

Preserve historical product information.

For example, changing a product's name or price tomorrow must not change the details of a sale made yesterday.

Use stable IDs and timestamps.

### Financial calculation rules

For each transaction:

Original total value = Original unit selling price × Quantity.

Total discount = Per-unit discount × Quantity.

Actual revenue = Original total value − Total discount.

Cost of goods sold = Purchase cost per unit × Quantity.

Realized gross profit = Actual revenue − Cost of goods sold.

For a basket, calculate these figures for each line item and then aggregate them.

Use a consistent currency precision and rounding strategy.

Never use floating-point calculations carelessly for financial amounts. Use integer minor units or an appropriate decimal representation.
